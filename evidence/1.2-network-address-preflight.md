# Control Center 1.2.x — Network address-change preflight

## Scope

Core B / Infrastructure adds a non-mutating preflight stage for the existing network address-change preview. The slice is intentionally limited to runtime interface identity/state freshness and recovery requirements; it does not add an apply executor or mutate host networking.

Implementation base: `1.2.x@d9e343968f0092ab01f22960db4c830d59c46047`.

Pre-edit WIP and ownership checks found no open Core B product PR. The only open `1.2.x` Core A feature PR, #227, is isolated to `internal/operations/**`, `internal/httpserver/operations_*` and its evidence file, so it does not own or overlap the network files in this slice.

## Contract

The existing admin-only `POST /api/v1/network/address-change/preview` remains the first step and now returns an additive `source_fingerprint` plus management capability metadata. The fingerprint binds the exact target interface runtime snapshot used for the preview: interface name/index, MTU, hardware address, link flags and assigned addresses are canonicalized before SHA-256 hashing.

A new admin-only `POST /api/v1/network/address-change/preflight` accepts the same desired interface/CIDR plus `expected_source_fingerprint`, re-inventories the host and reuses the existing address planner validation. Preflight fails closed when the target interface runtime snapshot has changed since preview, while preserving explicit Desired / Actual / Rollback evidence.

`apply_supported=false` remains authoritative. A passing preflight means only that the preview-to-preflight runtime snapshot is fresh and the requested state remains valid; it is not authorization to change host networking.

## Safety and recovery boundary

No network interface, route, resolver, service, file, privileged worker, state schema, secret, release metadata or deployment target is changed by this slice.

The preflight publishes required future executor steps:

1. identify the authoritative interface configuration owner;
2. back up the current interface configuration;
3. verify a recovery path before apply;
4. apply the desired address state;
5. verify management connectivity before commit;
6. roll back on verification failure.

Runtime interface evidence alone does not prove whether NetworkManager, systemd-networkd, netplan, ifupdown or another owner is authoritative. This slice therefore does not infer configuration ownership and deliberately leaves apply disabled until that recovery-aware executor boundary is implemented and independently reviewed.

Empty current address state is treated as a valid captured rollback state: rollback means restoring an empty address set rather than inventing a replacement address.

## Security / audit

- existing server-side authentication and admin role remain authoritative;
- existing CSRF/origin mutation validation is reused for preview and preflight;
- preview role denial is now audited consistently with the DNS infrastructure contract;
- preflight success, validation failure, permission denial, CSRF rejection and stale-source blocker outcomes are audited without request-body or credential material;
- malformed fingerprints are rejected before they can satisfy a handoff check;
- there is no new privileged command or arbitrary execution surface.
