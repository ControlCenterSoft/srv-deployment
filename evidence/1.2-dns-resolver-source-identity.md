## Scope

This slice strengthens the existing non-mutating DNS resolver inventory and preview/preflight evidence. It does not add a resolver writer, privileged helper, service restart, release change, or test-server mutation.

Additive API/object-model evidence:

- `source_mode`: topology observed at `/etc/resolv.conf` (`direct_resolv_conf`, `systemd_stub`, `systemd_uplink`, `systemd_static`, `network_manager_runtime`, `external_symlink`, or `other`);
- `source_manager`: manager inferred only when the observed symlink target is an upstream-documented path (`systemd_resolved`, `network_manager`, or `unknown`);
- `source_ambiguous`: explicit indication that file topology alone cannot attribute ownership safely;
- preview/preflight `warnings` for ambiguous ownership and for a local stub whose upstream resolver state is not authoritatively resolved;
- source identity is bound into the existing SHA-256 source fingerprint so a manager/topology change invalidates stale preview evidence even if nameserver/search/options values remain equal.

The previous preflight pass/fail contract is intentionally preserved. Ambiguous ownership is diagnostic evidence, not a new blocker, because direct `/etc/resolv.conf` is valid on supported Linux hosts and no apply executor exists yet. Any future apply implementation must define which source modes it can own and must keep fresh preview/preflight, backup, validation, apply/verify, and rollback/recovery gates.

## Upstream behavior used

Primary upstream documentation checked on 2026-08-22:

- NetworkManager `NetworkManager.conf`: https://www.networkmanager.dev/docs/api/latest/NetworkManager.conf.html
  - NetworkManager always writes its runtime resolver representation to `/run/NetworkManager/resolv.conf`;
  - `rc-manager` determines whether/how `/etc/resolv.conf` is written;
  - a symlink to `/run/NetworkManager/resolv.conf` is a documented special case;
  - NetworkManager auto-detects `systemd-resolved` when `/etc/resolv.conf` points to `/run/systemd/resolve/stub-resolv.conf`, `/run/systemd/resolve/resolv.conf`, `/lib/systemd/resolv.conf`, or `/usr/lib/systemd/resolv.conf`.
- systemd `org.freedesktop.resolve1`: https://www.freedesktop.org/software/systemd/man/247/org.freedesktop.resolve1.html
  - `ResolvConfMode` distinguishes `uplink`, `stub`, `static`, `foreign`, and `missing`; `foreign` explicitly means the file is managed by an administrator or another service.
- systemd network-manager integration guidance: https://systemd.io/WRITING_NETWORK_CONFIGURATION_MANAGERS/
  - `/run/systemd/resolve/resolv.conf` is the resolver-compatible file generated by `systemd-resolved`;
  - network managers should stop directly modifying `/etc/resolv.conf` when it points at the resolved-provided file.

Project choice: file topology is treated as evidence, not proof of the running daemon/configuration. A regular file or arbitrary symlink therefore remains `source_manager=unknown` / `source_ambiguous=true`. This slice does not query D-Bus, NetworkManager configuration, immutable flags, or process state and does not invent ownership semantics from file contents alone.
