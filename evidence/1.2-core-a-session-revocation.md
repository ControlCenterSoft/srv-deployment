# Control Center 1.2 — Core A session revocation evidence

Status: implementation evidence; merge remains owned by CC Integrator.

Base: `1.2.x@7353217ac4185226a34a0e09445a7a35268f9be3`.

## Bounded vertical slice

Adds one self-service session-security workflow without changing the session storage model or adding a data migration:

- `POST /api/v1/auth/sessions/revoke-others`;
- scope is always the authenticated principal; no username/user ID selector is accepted;
- the current session remains active and all other still-active sessions for the same user are revoked;
- sessions belonging to other users are never selected;
- response is bounded to `status` and `revoked_count` and never returns session cookies, token digests or CSRF material.

## Permission and security model

Permission metadata: `authenticated:self`.

The route uses the existing server-side session authority and does not grant a new RBAC capability over another principal. Before mutation it requires the existing CSRF token plus canonical-origin policy. `Manager.RevokeOtherSessions` revalidates the current opaque token while holding the same lock as the revocation pass; a missing, expired or foreign current token fails closed before any other active session can be deleted.

Raw session tokens remain browser-cookie material only. The session manager continues to index sessions by SHA-256 token digest; this slice does not log, persist or return plaintext session/token material.

## Validation and error contract

- anonymous request: `401 authentication_required`;
- missing/invalid CSRF or rejected origin: `403 csrf_rejected`;
- current session changing between authentication and mutation: fail closed as `401 authentication_required` and clear the presented cookie;
- success: `200 {"status":"other_sessions_revoked","revoked_count":N}`.

All API errors continue to use the platform error envelope and correlation/operation ID supplied by the existing request middleware.

## Operations, audit and health

Successful revocation is recorded as the persistent operation kind and audit action `auth.sessions.revoke_others`, actor/target bound to the authenticated username. CSRF/origin denials are audited with `csrf_rejected`. No new health/readiness dependency is introduced because the slice uses the existing in-process session manager and operation/audit stores already covered by readiness and diagnostics.

## Regression/acceptance coverage

`internal/auth/sessions_test.go` proves:

- only same-user non-current sessions are revoked;
- current session survives;
- another user's session survives;
- invalid and foreign current tokens fail closed without state change.

`internal/httpserver/auth_sessions_test.go` proves the API workflow end to end:

- authentication is mandatory;
- missing CSRF and foreign Origin are rejected without revocation;
- a valid request revokes the older same-user session while preserving the current one;
- `revoked_count` is bounded and deterministic for the fixture;
- operation history and audit expose the expected successful action.

The normal exact-head CI (`gofmt`, `go vet`, `go test ./...`, security/contract checks) is the merge gate for this branch.

## Upgrade, recovery and rollback

No schema, file-format, secret-store or installer change is introduced. Upgrade is therefore code-only and backward-compatible. Rollback is a code revert; already-revoked sessions intentionally remain revoked and users can authenticate again through the existing login path. There is no recovery migration to run and no privileged/root operation in this slice.
