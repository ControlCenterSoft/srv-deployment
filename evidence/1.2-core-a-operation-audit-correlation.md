## Contract

`GET /api/v1/operations/{id}` remains backward-compatible and keeps `contract_version=1`. The response now adds:

- `audit.events`: newest-first audit records whose `operation_id` exactly equals the requested operation ID;
- `audit.count`, `bounded=true`, `limit=100`;
- `audit.permission=audit.read`, plus `authorized` and `available` flags;
- `permissions.audit=audit.read`;
- `health.audit_log`, with `health.status=degraded` only when an audit-authorized caller cannot read the audit component.

Existing authentication, `operations.read` authorization, operation-ID validation and stable `invalid_operation_id` / `operation_not_found` / `permission_denied` errors are unchanged.

## Security and privacy boundary

- Correlated audit data is returned only when the authenticated principal also has `audit.read`.
- The implementation reuses the existing bounded AuditLog projection; it does not read arbitrary files or request bodies.
- Audit records retain the existing safe schema and do not add password, session, CSRF, token or credential fields.
- A correlation read is additive/read-only and does not change Desired/Actual state, privileged execution, release identity or server mutation behavior.
