# ADR-0009: Пользовательская ценность каждого релиза

- Статус: принято
- Дата: 2026-08-21
- Область: release governance / product delivery

## Контекст

Control Center развивается параллельными потоками: продуктовый функционал, инфраструктура, CI/CD, безопасность, серверный агент, документация и сайт. Технические изменения необходимы, но выпуск новой версии продукта без заметного расширения возможностей пользователя создаёт версионный шум и затрудняет оценку реального прогресса.

## Решение

Каждый новый релиз Control Center обязан включать как минимум одну завершённую доработку, которая расширяет пользовательский функционал.

### Определение пользовательской доработки

Пользовательской доработкой считается изменение, которое даёт пользователю новую доступную возможность либо заметно расширяет существующую возможность в интерфейсе, API или поддерживаемом пользовательском сценарии.

Примеры:

- новый раздел, действие, мастер или сценарий в UI;
- новая управляемая функция сервера, доступная из Control Center;
- новый пользовательский API/интеграционный сценарий;
- расширение существующей функции новыми параметрами, режимами или возможностями;
- устранение ограничения, которое открывает ранее недоступный пользовательский сценарий.

### Что само по себе не удовлетворяет правилу

Следующие изменения важны и могут входить в релиз, но не считаются достаточной причиной для нового продуктового релиза без пользовательской доработки:

- только рефакторинг;
- только CI/CD, workflow или build-изменения;
- только обновление зависимостей;
- только документация;
- только тесты;
- только внутренние изменения агента/transport layer, если пользовательские возможности не расширились;
- только исправления инфраструктуры или deployment;
- только оптимизация производительности без изменения пользовательского сценария.

## Release gate

Перед присвоением новой версии интегратор обязан зафиксировать минимум одну `User-facing improvement` и подтвердить:

1. что она завершена и доступна пользователю;
2. что для неё есть тесты или проверяемое acceptance evidence;
3. что она описана в release notes;
4. что полный acceptance релиза зелёный.

Если в наборе изменений отсутствует пользовательская доработка, изменения должны накапливаться в рабочей ветке/maintenance PR и не должны самостоятельно инициировать новый продуктовый релиз.

## Исключения

Экстренное security/hotfix-исправление может быть выпущено без новой пользовательской функции, если задержка создаёт риск безопасности, потери данных, недоступности продукта или нарушает возможность обновления/rollback. Такой выпуск должен быть явно помечен как `emergency maintenance release` и не отменяет правило для следующего обычного релиза.

## Последствия

- Версии Control Center отражают видимый продуктовый прогресс.
- Инфраструктурные и технические работы продолжаются независимо, но не создают версионный шум.
- Release notes должны явно содержать секцию пользовательской ценности.
- Автономный интегратор обязан блокировать обычный релиз без хотя бы одной пользовательской доработки.
