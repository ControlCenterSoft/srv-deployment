# Control Center 2.2.0 — канонический план новой линии

Статус: **bootstrap implementation / development**

Последнее обновление: 2026-08-18

## 1. Исходная точка

Control Center 2.2.0 начинается как новая чистая линия разработки.

Состояние предыдущей production-линии до 2.1.4 сохранено в архивной ветке:

`archive/pre-2.2.0-2026-08-18`

Рабочая ветка новой линии:

`release/2.2.0`

Production `main` и `deployment.json` на 2.2.0 пока не переключены.

Новая линия не должна автоматически наследовать старую функциональную структуру, старые названия разделов или внутреннюю связанность предыдущих релизов. Совместимость рассматривается отдельно и только там, где она явно требуется.

## 2. Этап 1 — самостоятельный установщик web-интерфейса

Первым компонентом 2.2.0 создаётся независимый установщик web-интерфейса Control Center.

### Требования этапа 1

- установка web-интерфейса как отдельного воспроизводимого компонента;
- сохранение утверждённого ранее визуального дизайна Control Center;
- чистая установка без зависимости от установленной предыдущей версии Control Center;
- идемпотентный повторный запуск установщика;
- обязательный preflight до внесения изменений;
- резервное копирование изменяемых конфигураций;
- health/acceptance-проверка после установки;
- отсутствие секретов и учётных данных в Git;
- единый shell для подключения будущих модулей;
- отсутствие жёсткой зависимости shell от конкретных сервисов.

### Фактически реализовано на текущем bootstrap

- независимый WSGI web-shell;
- системная PAM-аутентификация локальными Linux identities;
- подписанная web-сессия;
- отдельный session key на хосте;
- маршруты четырёх разделов;
- публичный `/api/v1/health`;
- nginx reverse proxy;
- systemd unit `control-center-web.service`;
- базовый sandbox hardening;
- `installer/install.sh`;
- `installer/acceptance.sh`;
- GitHub Actions validation gate.

Реализация этапа 1 ещё должна пройти полноценную clean-host acceptance перед признанием этапа завершённым.

## 3. Главное меню 2.2.0

В базовой навигации допускаются только следующие верхнеуровневые пункты.

### 3.1. Обзор

Маршруты: `/` и `/overview`.

Назначение:

- стартовая страница;
- общее состояние Control Center и хоста;
- сводные карточки состояния будущих модулей;
- единая точка общего health/status представления.

### 3.2. Маркет

Маршрут: `/market`.

Это новое название раздела, ранее называвшегося «Сервисы».

Назначение:

- каталог доступных модулей;
- установка и удаление компонентов;
- запуск и остановка;
- переход к настройкам установленного компонента;
- расширение каталога без изменения главного меню.

Планируемый единый lifecycle-контракт модулей:

- `not_installed` — Не установлен;
- `installed` — Установлен;
- `running` — Запущен;
- `stopped` — Остановлен;
- `error` — Ошибка.

Планируемые действия:

- Установить;
- Удалить;
- Запустить;
- Остановить;
- Настроить.

Конкретный module manifest/API-контракт будет закреплён отдельным шагом до начала реализации функциональных карточек Маркета.

### 3.3. RBAC

Маршрут: `/rbac`.

Это новое название раздела, ранее называвшегося «Пользователи».

Назначение:

- управление субъектами доступа;
- управление ролями;
- назначения ролей;
- разрешения;
- единое представление локальных и будущих доменных identities.

Текущая PAM-аутентификация этапа 1 является bootstrap-механизмом входа и не заменяет будущую полноценную RBAC-модель.

### 3.4. Система

Маршрут: `/system`.

Назначение:

- параметры Control Center и хоста;
- обновления;
- диагностика;
- резервное копирование и восстановление;
- журналы;
- общие системные настройки.

Эти функции добавляются по мере реализации последующих этапов.

## 4. Навигационный контракт

Канонические маршруты новой линии:

- `/` и `/overview` → Обзор;
- `/market` → Маркет;
- `/rbac` → RBAC;
- `/system` → Система.

Старые названия «Сервисы» и «Пользователи» не используются в UI 2.2.0.

Если позднее потребуется URL-совместимость, она реализуется только redirect-механизмом и не должна возвращать старые названия в интерфейс.

## 5. UI/design contract

Сохраняется визуальная идентичность Control Center:

- бренд CONTROL CENTER;
- характер login/admin console;
- существующая логика административной компоновки;
- единая стилистика shell-интерфейса.

В 2.2.0 меняется архитектура и информационная структура, а не визуальная идентичность продукта.

UI shell должен оставаться независимым от конкретных устанавливаемых компонентов.

## 6. Authentication и session contract этапа 1

На bootstrap-этапе:

- используется существующая локальная Linux-учётная запись;
- проверка пароля выполняется через PAM;
- отдельный bootstrap web-пароль Control Center не создаётся;
- session signing key создаётся на хосте при установке;
- секрет не хранится в Git;
- session contract должен быть заменяемым без переписывания UI shell при внедрении расширенной identity/RBAC архитектуры.

## 7. Installer contract

Установщик этапа 1 должен:

1. проверить root/systemd/apt окружение;
2. установить минимальные зависимости;
3. создать каталоги Control Center;
4. сохранить резервные копии изменяемых системных конфигураций;
5. загрузить application payload из ветки 2.2.0;
6. создать session key при его отсутствии;
7. создать/обновить systemd unit;
8. настроить nginx reverse proxy;
9. запустить сервисы;
10. выполнить backend и nginx health acceptance;
11. завершиться `INSTALL PASS` только после успешной проверки.

Повторный запуск не должен разрушать существующий рабочий bootstrap.

## 8. Acceptance contract этапа 1

Минимально проверяются:

- systemd service активен;
- backend отвечает;
- `/api/v1/health` возвращает `status=ok`;
- health contract сообщает продукт `Control Center` и версию `2.2.0`;
- nginx проксирует health endpoint;
- основные UI-маршруты существуют;
- установка не зависит от старой production-линии.

Дополнительно обязательна реальная clean-host проверка до объявления этапа завершённым.

## 9. Граница завершения этапа 1

Этап 1 считается завершённым, когда с чистой поддерживаемой системы одним установщиком разворачивается работоспособный Control Center shell с:

- сохранённым дизайном;
- рабочей аутентификацией;
- session contract;
- health endpoint;
- nginx/systemd integration;
- четырьмя разделами: Обзор, Маркет, RBAC, Система;
- повторяемой acceptance-проверкой.

Полная бизнес-логика Маркета, полноценная RBAC-модель и расширенные функции Системы не блокируют завершение платформенного bootstrap.

## 10. Следующий этап

После стабилизации bootstrap следующий основной блок — **Маркет**.

До реализации конкретных сервисов необходимо отдельно закрепить:

- формат manifest модуля;
- идентификатор и версия модуля;
- зависимости;
- lifecycle states;
- install/remove/start/stop/configure hooks;
- health/status contract;
- rollback/error model;
- права доступа RBAC для операций с модулями;
- правила отображения карточки в UI.

После закрепления этого контракта модули должны подключаться к Control Center без изменения базового shell.
