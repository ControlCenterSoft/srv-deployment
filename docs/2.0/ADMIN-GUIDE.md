# Control Center 2.x — руководство администратора

## 1. Интерфейс

В 2.x используется единая оболочка Control Center с левой навигацией, верхней строкой состояния, поиском по разделам и рабочими модулями внутри общей области. Основные разделы: Обзор, Сеть, DHCP, PXE Windows, PXE Linux, Домен и доступ, Сетевые ресурсы, Minecraft, Загрузки, AdGuard VPN, Сервисы, Пользователи и Система.

## 2. Система и обновления

В модуле **Система** блок автоматического обновления показывает:

- **Автоматическое обновление** — включено/выключено и интервал проверки;
- **Последняя проверка обновления** — время последнего обращения к источнику обновлений;
- **Последнее успешное обновление** — время последней полностью принятой транзакции обновления.

`Последняя проверка обновления` не означает, что обновление устанавливалось. `Последнее успешное обновление` не должно изменяться после простой проверки, неудачной попытки или отклонённого релиза.

Механизм 2.x использует транзакционный `srvcc-update-controller`. Неудачный fingerprint релиза блокируется от повторного автоматического применения, но периодические проверки продолжаются. Новый fingerprint может быть рассмотрен снова. После обновления автоматический timer принудительно проверяется на enabled/active, чтобы ошибка установки не оставляла сервер без дальнейших проверок.

## 3. Резервные копии

В разделе резервных копий доступны выбор отдельных архивов, **Выбрать все** и **Удалить выбранные**. Массовое удаление проходит через административный API, CSRF-проверку и очередь привилегированных действий; максимальный размер одной операции ограничен 200 архивами.

Настройка `backup_before_update` является авторитетной. Если она выключена, Control Center не создаёт пользовательскую копию перед обновлением. Внутренняя rollback-копия транзакции всё равно создаётся и не считается плановым/пользовательским backup.

Плановое резервное копирование управляется отдельно. При выключенном расписании `srv-control-backup.timer` должен быть disabled/inactive после применения конфигурации или обновления.

## 4. DHCP

Раздел **DHCP** позволяет задать интерфейс, сеть, маску, диапазон адресов, шлюз, DNS и время аренды. Поддерживаются дополнительные DHCP options с кодами 1–254, резервирования MAC → IP и просмотр текущих аренд.

Системные PXE options управляются Control Center и не должны дублироваться произвольными пользовательскими options.

## 5. PXE Windows и Linux

PXE-функциональность доступна только после установки соответствующего сервиса. ISO загружается в Control Center, проверяется и публикуется как PXE-образ.

Установка на ПК **запрещена по умолчанию**. Для установки необходимо создать профиль для конкретного MAC-адреса и отдельно разрешить установку. Разрешение одноразовое. Если профиль отсутствует или не авторизован, boot/install payload не выдаётся.

Профиль ПК может содержать IP из DHCP, имя компьютера, образ ОС, профили ПО, профили параметров и параметры ввода в домен. Для Windows поддерживается выбор редакции образа; перед очисткой диска проверяется WIM/index. Для Linux применяются защитные проверки boot architecture, Secure Boot и выбора диска.

PXE boot media публикуется через `/pxe/files`, при этом приватные профили `/srv/pxe/profiles` напрямую наружу не публикуются.

## 6. Minecraft Bedrock

2.x использует health-first восстановление. Сначала проверяются сервис, UDP listener и активный мир. Исправный сервер не переустанавливается.

Если сервер неисправен, выполняется безопасное восстановление через проверенный single-server management path: backup, update/repair, restart и повторная health-проверка. Замена мира разрешается только если обычное восстановление не помогло и safety backup успешно создан. Recovery world получает имя вида `ControlCenter-Recovery-*`.

Если необходимые проверенные legacy helpers отсутствуют, релиз должен остановиться, а не выполнять неподтверждённую разрушительную переустановку.

## 7. Диагностика обновлений

При проблемах проверять в таком порядке:

1. состояние блока обновления в UI;
2. `github-update-status.json`: `last_check_at`, `last_update_attempt_at`, `last_successful_update_at`, `stage`, `blocked_fingerprint`;
3. состояние `srvcc-github-agent.timer` и `srvcc-github-agent.service`;
4. release fingerprint и причину блокировки;
5. результаты preflight/apply/acceptance текущей транзакции.

Повторяющиеся попытки одного и того же уже отклонённого fingerprint не являются нормальным поведением 2.x.

## 8. Диагностика backup

Если backup создаётся при выключенной опции перед обновлением, необходимо проверить фактическое boolean-значение `backup_before_update`: в 2.x только JSON `true` включает эту функцию. Строки вроде `"false"` не должны считаться истиной.

Если выключено плановое резервное копирование, дополнительно проверить состояние `srv-control-backup.timer`.

## 9. Диагностика PXE

Проверить: установлен ли PXE-сервис, существует ли опубликованный образ, совпадает ли firmware/architecture клиента, существует ли профиль MAC, выдано ли одноразовое разрешение и не было ли оно уже consumed. Для DHCP дополнительно проверить правильность LAN interface/network и наличие корректного next-server.

## 10. Безопасность изменений

Изменения системных сервисов выполняются через backend/agent, а не прямыми командами из браузера. Административные операции требуют сессию, права RBAC и CSRF. При обновлении 2.x необходимо сохранять обратимый rollback snapshot до изменения рабочих файлов и units.
