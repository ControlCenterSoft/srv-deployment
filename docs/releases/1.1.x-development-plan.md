## Рабочая модель

Каждая новая функция начинается от актуальной `1.1.x` в короткой ветке `feature/1.1-*`.
Один PR — один проверяемый вертикальный срез. Изменения интерфейса, backend/API, privileged operations и tests разделяются, если могут быть приняты независимо.

### Продуктовый release gate

Каждый обычный новый релиз Control Center должен содержать минимум одну завершённую **User-facing improvement**: новую пользовательскую capability либо заметное расширение существующего сценария в UI/API/поддерживаемом workflow.

Release notes обязаны явно фиксировать:

- пользовательскую доработку;
- acceptance evidence, подтверждающее доступность и корректность сценария;
- известные ограничения, если они остаются.

Refactor, CI/CD, dependencies, documentation, tests, infrastructure, internal agent/transport и performance-only changes разрешено интегрировать и накапливать, но они не должны самостоятельно инициировать обычный продуктовый release. Исключение — явно обозначенный emergency maintenance/security/hotfix release, когда задержка создаёт риск безопасности, потери данных, недоступности продукта либо нарушает update/rollback.

### Fast gate

Fast CI классифицирует changed paths и запускает только применимые проверки:

- policy/secret scan — всегда;
- Go — format/vet/unit+contract tests;
- shell/install — syntax;
- AI integrations — Python/regression tests;
- runtime — быстрый linux/amd64 build;
- docs-only — без runtime build.

Stable `1.0.0` не пересобирается на каждом feature commit.

### Full candidate gate

После merge/push в `1.1.x` полный acceptance exact SHA должен подтвердить:

1. полный deterministic validation;
2. reproducible amd64 + arm64;
3. exact rebuild stable `1.0.0`;
4. disposable root/systemd install;
5. signed update + rollback;
6. auth/operations/repair acceptance;
7. staging package;
8. real test-server update либо безопасный exact-identity no-op, включая совместимость с фактически установленным updater path;
9. health/readiness/version verification на реальном сервере.

Production promotion запрещён без `REMOTE_STAGING=PASSED`.

## AI-assisted development

AI-контуры разделены по ролям и не являются runtime-зависимостями:

- ChatGPT — orchestration и implementation integration;
- Gemini — независимый code review;
- Perplexity — current external research по официальной документации, compatibility, deprecations/migrations и security advisories;
- deterministic CI/tests — авторитетный gate.

Gemini/Perplexity не получают deployment privileges. Diff считается недоверенным входом.

## Remote staging configuration

Full acceptance активирует real-server staging, когда в GitHub repository secrets настроены:

- `CONTROL_CENTER_STAGING_HOST`;
- `CONTROL_CENTER_STAGING_USER`;
- `CONTROL_CENTER_STAGING_SSH_KEY`;
- `CONTROL_CENTER_STAGING_KNOWN_HOSTS`;
- `CONTROL_CENTER_STAGING_SIGNING_KEY`;
- опционально `CONTROL_CENTER_STAGING_PORT`.

SSH host key обязан быть pinned. Staging signing key не используется для production releases.

## Merge и release train

PR в `1.1.x` создаётся из короткой feature/fix/docs ветки. После обязательного fast gate оркестратор может включить native auto-merge для допустимых изменений. Каждый candidate должен иметь exact SHA и собственное acceptance evidence. Неуспешный candidate не объявляется принятым документацией.

`main` и canonical `deployment.json` остаются на `1.0.0` до отдельного promotion change, который может быть принят только при green full acceptance и реальном staging evidence.
