# Control Center 1.1.x — план линии разработки

Статус: development

## Baseline

- production baseline: 1.0.0;
- accepted source commit: `1b364ae88789696bf98537d21544de8a259d086d`;
- development integration branch: `1.1.x`;
- candidate train: `1.1.0-rc.<GitHub Actions run number>`.

## Рабочая модель

Каждая новая функция начинается от актуальной `1.1.x` в короткой ветке `feature/1.1-*`.
Один PR — один проверяемый вертикальный срез. Изменения интерфейса, backend/API, privileged
operations и tests разделяются, если могут быть приняты независимо.

### Fast gate

Fast CI классифицирует changed paths и запускает только применимые проверки:

- policy/secret scan — всегда;
- Go — format/vet/unit+contract tests;
- shell/install — syntax;
- AI integrations — Python/regression tests;
- runtime — быстрый linux/amd64 build;
- docs-only — без runtime build.

Stable 1.0.0 не пересобирается на каждом feature commit.

### Full candidate gate

После merge/push в `1.1.x` автоматически вызывается full acceptance exact SHA:

1. полный deterministic validation;
2. reproducible amd64 + arm64;
3. exact rebuild stable 1.0.0;
4. disposable root/systemd install;
5. signed update + rollback;
6. auth/operations/repair acceptance;
7. staging package;
8. real test-server update и health/readiness/version verification, если staging transport настроен.

Production promotion запрещён без `REMOTE_STAGING=PASSED`.

## AI-assisted development

AI-контуры разделены по ролям и не являются runtime-зависимостями:

- ChatGPT — orchestration и implementation integration;
- Gemini — независимый code review;
- Perplexity — current external research по официальной документации, compatibility,
  deprecations/migrations и security advisories;
- deterministic CI/tests — авторитетный gate.

Gemini/Perplexity не получают deployment privileges. Diff считается недоверенным входом.

## Remote staging configuration

Full acceptance автоматически активирует real-server staging, когда в GitHub repository secrets
настроены:

- `CONTROL_CENTER_STAGING_HOST`;
- `CONTROL_CENTER_STAGING_USER`;
- `CONTROL_CENTER_STAGING_SSH_KEY`;
- `CONTROL_CENTER_STAGING_KNOWN_HOSTS`;
- `CONTROL_CENTER_STAGING_SIGNING_KEY`;
- опционально `CONTROL_CENTER_STAGING_PORT`.

SSH host key обязан быть pinned. Staging signing key не используется для production releases.

## Merge и release train

PR в `1.1.x` создаётся из `feature/1.1-*`. После обязательного fast gate оркестратор может
включить native auto-merge. Каждый интеграционный commit получает собственный RC identity и full
acceptance evidence. Неуспешный RC не переписывается: следующая интеграция создаёт новый RC.

`main` и canonical `deployment.json` остаются на 1.0.0 до отдельного promotion change, который
может быть принят только при green full acceptance и реальном staging evidence.
