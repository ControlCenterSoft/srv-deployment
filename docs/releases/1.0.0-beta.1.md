# Control Center 1.0.0-beta.1 — Safe Update Foundation

Status: implementation candidate

## Goal
Introduce the first cryptographically verified, rollback-capable update foundation while preserving the security, RBAC, state, operations, audit and diagnostics contracts accepted in alpha.3.

## Implemented scope
- Immutable release directories under `/usr/local/lib/control-center/releases/`.
- Atomic `current` and `previous` symlink activation model.
- Migration from the alpha single-binary install layout without deleting state.
- Ed25519-signed release manifest schema `1`.
- SHA-256 and exact artifact-size verification.
- Signed OS/architecture and state-schema compatibility bounds.
- Strict SemVer validation and precedence comparison without machine-integer overflow for arbitrarily large numeric identifiers.
- RFC3339 build timestamp validation.
- Strict three-entry release package whitelist.
- Trusted-current-runtime verification before candidate execution.
- Candidate embedded version/commit consistency check after cryptographic verification.
- Local release packaging tool for signed update archives.
- Root updater `/usr/local/sbin/control-center-update`.
- Same-version and downgrade rejection by default with explicit controlled `--allow-downgrade` escape hatch.
- Post-update health/readiness/version gate.
- Automatic atomic rollback to previous known-good runtime when post-update acceptance fails.
- Preserved update public trust across repair/reinstall/non-purge uninstall.
- Configurable installer/update acceptance URL for non-default deployment layouts.
- Regression carry-forward from real-host alpha.3 acceptance: restricted systemd directory modes and correct `[hidden]` Web UI behavior.
- CI scenarios for signed packaging, install/restart, Auth/RBAC, Operations/Diagnostics and signed update rollback acceptance.

## Release package contract
A beta update package is a gzip tar containing exactly:

```text
manifest.json
manifest.sig
control-center
```

The package contains no private signing key.

## Signed manifest schema 1
The manifest authenticates:

```text
schema
product
version
channel
commit
built_at
os
arch
state_schema_min
state_schema_max
artifact.name
artifact.sha256
artifact.size
```

## Update acceptance scenarios
The system test exercises:
1. valid signed update to a newer version;
2. same-version rejection without changing `current`;
3. modified candidate bytes rejected before candidate execution;
4. package-whitelist rejection for an unexpected tar entry;
5. correctly signed package for the wrong architecture rejected;
6. correctly signed downgrade rejected without explicit override;
7. tampered signed metadata rejected;
8. correctly signed but intentionally broken runtime, requiring automatic rollback and recovery of the prior release.

## Out of scope
- Remote channel/index service and automatic download.
- Web-triggered self-update.
- Production signing-key lifecycle/HSM integration.
- Automatic retention/garbage collection of old release directories.
- Privileged worker implementation.
- State migrations beyond schema `1`.
- Commercial licensing/support-agent behavior.

## Promotion gates
Before beta.1 can be considered accepted rather than an implementation candidate:
- local full validation must pass;
- GitHub branch integrity must be verified;
- root/systemd acceptance must pass on a real test host;
- the real host must demonstrate signed update success plus rollback from a signed broken candidate;
- evidence must be retained in the diagnostics/evidence channel.
